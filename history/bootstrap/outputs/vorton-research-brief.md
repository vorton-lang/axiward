# Vorton 研究底稿

整理日期：2026-09-16。用于接续讨论；不代表批准实施某套架构，也不变更仓库路线图。

## 1. 我们要做什么

**研究从开放意图到可验收产品的完整项目流程，并使 agent 能承担其中的工程推进责任。**

代表性起点是：“我想要一个很 cool 的 PL，实现一个。”终点是用户能实际使用、评价和验收的语言与实现。需求形成、方案探索、实现和交付都属于研究范围。

用户已经明确的方向：

- 人提供宏观意图，参与必要的方向对齐并验收效果；agent 承担调查、方案形成、工程决策、实现、验证和纠偏。人无需下场写代码或接管日常工程调度。
- 流程应当适用于人或 agent 执行项目。先理解有经验的开发者如何完成开放任务、使用哪些能力和外部支持，再判断 agent 的具体缺口。
- 初始目标中的一部分具体含义可能在方案、原型和反馈中逐渐形成；不能假定用户事先藏着一份完整需求，等待被逐项问出来。
- 系统应支持 agent 完成目标，或明确说明未完成部分及障碍。
- Vorton 的定位已经转向完整的反馈系统。工具集、集成现有 harness、自建 harness 都是待比较的实现形态。
- 控制论与信道问题是主要探索方向。
- 以现有模型为起点；本轮研究不能依赖继续训练模型。
- 新的流程设计标准：初级程序员遵守规范，也能对项目作出推进；不能把高级判断隐藏在“选择正确架构”“写正确测试”等要求里。
- 当前设计重点是区分可固化规则与任务所需自由度，不以对 agent 自身缺陷的推测作为设计依据。
- 可表达的保证优先利用现有类型、构造约束和形式验证工具；普通测试作为有限观测，不能直接承担通用正确性保证。

评估维度建议：最终产品是否满足逐步明确的用户期待、真实完成率、错误宣称完成、无效反复、资源消耗、人工介入负担。必要的产品讨论与人接管工程工作的负担应分别记录。指标定义和目标值尚未确定。

## 2. 我们的问题是什么

| 问题 | 需要得到的具体答案 |
|---|---|
| 人如何完成开放项目 | 在信息不完整时，有经验的开发者如何形成方案、安排工作、学习未知部分，并最终交付？使用了哪些工具、记录和协作支持？ |
| 目标与方案如何形成 | 如何通过研究、实例、原型和用户反馈共同明确要做的东西？哪些决定归用户，哪些属于工程责任？ |
| agent 究竟缺什么 | 对照具体工作环节，区分模型能力不足、信息或工具缺失，以及已有能力未被持续调用。每项缺口需要证据。 |
| 判断凭什么可信 | 判据、实现、实验和结果解释都可能由模型产生。哪些证据能暴露它们共同依赖的错误假设？ |
| 反馈如何改变路线 | 为什么反例出现后，agent 仍会把问题解释成局部遗漏？什么信号足以触发调查、改路或撤回结论？ |
| 如何保持推进 | 什么可以自主决定、什么应通过环境查明、什么值得消耗一次人工介入？怎样防止反复撞墙和过度暂停？ |
| 如何判断设计有效 | 在相同模型、预算与人工介入条件下，怎样测出系统确实改善任务结果？ |

已知现象：用户描述了“自信推进、反复局部修补、很晚才发现死胡同”的工作流痛点。#74 另外记录了“常规检查通过但语义错误”和“核心证明通过但调用者漏登记”的具体故障。它们是完整项目流程中部分环节的案例材料；研究范围还包括正常情况下的需求形成、主动探索、组织实现和交付。两类失败材料的关系需要通过原始轨迹调查，不能直接宣称共同根因已经确定。

## 4. 当前产物与证据缺口

已形成[人类团队与 agent 对照初稿](vorton-human-team-agent-comparison.md)：包含从开放意图到验收的活动、具体 PL 场景、可观察的 agent 风险，以及 Go、Rust、FeatureBench 和多 agent 研究的来源与适用边界。当前为有资料支持的推演，尚未进行替换实验。

已形成[工作流固定部分设计草案](vorton-workflow-core-design.md)：给出任务自由度、工作单元、探索与接纳路径、结果类型、初级执行者操作规则，以及拟由类型系统与 Verus 承担的核心不变量。当前只有设计，尚未实现或证明。

仍需补充：

- 用真实成功项目的原始记录核查活动图，包括实际顺序、往返和决策依据。
- 每项活动中 agent 的实测表现，以及模型能力、信息工具和流程问题的区分。
- 一份把原始目标、agent 判断、当时可见证据、动作和后果对齐的失败轨迹。
- 面向新定位的明确任务范围和成功标准。
- 各候选方法的适用前提，以及它们具体针对哪种失败。
- 可比较的基线、对照实验与结果。

这是本次讨论尚未建立的内容，不是对整个仓库或全部历史工作的缺失断言。

## 5. 当前设计议程

用户已将重点推进到“工作流能固化到什么程度，以及如何设计这些固定部分”。当前以[固定部分设计草案](vorton-workflow-core-design.md)为讨论对象。首个实现应只覆盖一个具体工作单元的规格、候选、依据和接纳路径，验证初级执行者能按明确义务推进，同时不能越过未完成义务。

人类项目过程与历史案例继续用于检查职责是否遗漏。此前 agent 风险栏只作为未经本项目实验验证的假设，不作为固定流程的设计前提。

下一步需具体化的三个设计问题：

1. 哪个真实工作单元适合作为最小实例，义务如何从已有语义取得？
2. 候选、规格、生产入口与机器检查结果如何绑定，接纳条件怎样实现？
3. 如何同时展示一条真正能推进的路径，以及缺证据或改变前提时无法越过的边界？

开放目标的形成、路线选择和调度仍保留为任务决策。固定核心只对已经明确表达的规则负责，不把语义判断伪装成机器保证。
