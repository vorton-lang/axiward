## E0：2026-09-17 的只读调查结果

本轮仅查资料、查询工具和整理计划，没有安装验证工具、运行候选证明或改动 Axiward 源码。

| 已观察到的事实 | 意味着什么 |
| --- | --- |
| 用户选择先验证 Lean 4 | Lean 为优先探索路线；不是对全部实现栈的最终确认。 |
| Windows PATH 未找到 `lean`、`lake`、`elan` | 实验前需检查或准备指定版本，不能声称已经验证过程序。 |
| 本机有 Rust 工具链，包括 1.98.1 | 可供后续需要的 Rust 工具使用；不改变 Lean 优先级。 |
| 注册表列出 WSL2 的 Ubuntu-22.04 | 存在候选 Linux 环境；本轮未验证其运行和隔离能力。 |
| 当前 Codex 为 `0.155.0-alpha.2.6` | 之前 `0.154.0-alpha.6.2` 的规则检查保留为历史证据，接入实验需记录并检查实际版本。 |

官方资料支持的判断：

1. **Lean 可在 Windows 原生运行。** Windows x86-64 属于其正式测试平台；调查时最新稳定发布为 `v4.34.0`。[平台说明](https://lean-lang.org/doc/reference/latest/platforms/)、[发布版本](https://github.com/leanprover/lean4/releases/tag/v4.34.0)
2. **可信验收需要核对目标和假设。** Lean 的验证资料描述了与受信目标比对、核对允许公理、重新检查证明的流程。[证明验证说明](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)
3. **隔离与版本需要单独闭合。** Lake 文档的默认审查隔离依赖 Linux；导出文件模式本身不证明导出与工作区源码对应。独立 Comparator 仓库当前又声明使用 `v4.35.0-rc2`，不能把各组件的“最新版”直接拼装。[Lake 文档](https://lean-lang.org/doc/reference/latest/Build-Tools-and-Distribution/Lake/)、[Comparator 工具链声明](https://github.com/leanprover/comparator/blob/master/lean-toolchain)
4. **证明与运行实现必须绑定。** Lean 的 `implemented_by` 可以替换编译使用的实现，而不自动证明替换等价；因此只检查逻辑定理还不够。[编译属性说明](https://lean-lang.org/doc/api/Lean/Compiler/ImplementedByAttr.html)

E0 完成的是资料与环境调查，不构成 M0 的运行通过证据。

## 工作包一览

| ID | 动作 | 目标 | 依赖 |
| --- | --- | --- | --- |
| M0-L1 | 探索 | 用 Lean 表达 Q0，打通实际实现、证明和构建 | R0、Q0、D3 |

L1 与 H1 可以分别调查，不意味着已经启动并行 agent。后续工作包仅在必要前提成立后进入实验。

### 已获得的 L1 结果

Lean 4.34.0 在 Windows 原生环境中完成 Q0 的实现、证明、内核复查及 EXE 构建运行。把入队改成插入队头后，错误实现能编译，但原规格及证明不变时检查失败。输入快照、一次失败尝试和成功记录均已保留。

见 [M0-L1 实验报告与复现工程](axiward-m0-l1/README.md)。该结果仅满足 L1；不把普通构建、哈希或运行观测提升为 L2 的可信自动接纳保证。

## M0-L1：实现、证明与构建

- **输入**：Q0 六条行为要求，候选 Lean 及审查工具版本。
- **影响范围**：独立实验目录、指定版本工具和样例文件；不改正式项目源码。
- **提交物**：Q0 到 Lean 定义与命题的对应表、最小队列实现及证明、可构建产物、版本与命令记录、明确的可信假设。
- **通过条件**：实现覆盖六条要求；证明针对实际定义；同一批固定输入可构建运行。零容量、满和空的情况都在命题范围内。
- **限制**：此包只确认实现与证明链可运行，不单独宣称自动接纳边界可靠。

## M0-H1：权限分离

- **输入**：CLI 设计中的目录布局、原生路径权限和指定命令例外。
- **影响范围**：临时视图、临时仓库、受保护的试验入口与测试任务配置；不把限制应用到其他用户任务。
- **提交物**：实际访问结果、权限配置与版本、允许和拒绝案例的记录。
- **通过条件**：普通 agent 命令不能直接读写仓库；指定入口能完成允许操作；`decide` 不向 agent 放行；同名程序、通用 shell 和参数伪装不能取得该例外；其他任务不受干扰。
- **限制**：纯规则匹配结果不能代替实际访问实验。若需要超出试验范围的系统权限改动，先记录缺口，再单独形成具体操作方案。

## M0-L2：可信证明接纳

**当前执行前提（D6）**：在完全访问权限下继续固定规格、公理检查、故障对照和产物绑定实验。恶意代码的进程隔离暂未成立，单独记为欠项；不把本轮结果描述为已具备完整的敌对候选接纳边界。

**实际结果**：正确候选通过；错误 FIFO、目标偷换、额外公理、sorry、旧证明、候选自身的未检查运行替换、规格替换与接纳后篡改均未被错误接纳。见 [L2 报告](axiward-m0-l2/README.md)。检查器自身的形式验证仍属 M1。

- **输入**：受保护的 Q0 机器规格、L1 候选产物、固定的审查工具链和已核实隔离条件。
- **影响范围**：实验输入及审查输出；候选不能改写规格、审查器或其策略。
- **提交物**：可复现的接纳流程、允许假设清单、目标与源码及构建产物的绑定记录、失败案例。
- **通过条件**：正确候选可接纳；错误 FIFO 实现、偷换目标、未授权公理或未完成证明、失效证据，以及未经认可的运行实现替换，都不能被误判为合格。
- **限制**：只验证一个导出证明，不等于验证了工作区代码或最终二进制。原生 Windows 与 WSL 的接法需据实验选择；使用 WSL 时，还需检查宿主目录挂载等访问路径。

## M0-H2：执行记录

- **输入**：原生 harness 的执行事件、固定输入快照和实验契约。
- **影响范围**：相关测试任务的记录采集及归档。
- **提交物**：实际调用、输入版本、环境、原始结果和记录来源的绑定方式。
- **通过条件**：模型自行编写的成功报告不能成为系统事实；错误任务、错误版本、截断或缺失记录得到正确识别；普通观测与证明依据保持区分。

## M0-H3：用户决定与恢复

- **输入**：一个待决事项、具体产物与规格版本，以及等待该答复的任务。
- **影响范围**：独立用户确认入口和指定测试任务的通知。
- **提交物**：决定记录、来源与作用范围、通知结果。
- **通过条件**：只有用户入口能作出该决定；决定准确关联事项与版本；能够通知目标任务；通知失败不丢失决定，也不被记录成恢复成功。

## 结果处理与下一步

每包保存输入版本、具体动作、实际结果和证据引用。通过、失败、环境不满足、尚未解决分别记录。

本轮探索有明确的问题边界，不设工作包自动过期。发现平台能力不足、目标被偷换或证据无法绑定时，保留结果并重新精化路线，不降低 R0 或 Q0 的验收要求。

本轮原型验证结果见 [M0 汇总](axiward-m0-results.md)。进入 M1 状态契约、纯内核与机器证明；原生强制隔离、正式 UI 和重启后任务定位继续作为明确后续项，不混入已通过的结论。
