# Vorton 工作流固定部分：设计草案

日期：2026-09-16。状态：设计规格，尚未实现或经机器证明。

## 1. 设计目标

**让初级程序员按照规范工作，也能推进项目；未解决的问题和错误尝试不能悄悄变成正式保证。**

这要求规范提供明确的可执行义务、修改边界和结果处理规则。“选择正确架构”“写好测试”“自行判断风险”仍然包含开放判断，不能作为已经固化的机制。

本设计不依赖对 agent 内部心理的推测，适用于人或 agent 执行。

必须区分两个目标：

- 可机械保障：在明确的规格和执行边界内，禁止无依据接纳、使用过期证据、静默削弱承诺和失败时破坏基线。
- 仍需研究：怎样从开放意图形成合适的规格，怎样选择有价值的探索，以及怎样解决难题。遵守流程本身不证明任意项目一定成功。

## 2. 固定什么，保留什么

| 责任 | 固定的规则 | 留给任务的自由度 |
|---|---|---|
| 目标 | 保留用户原始意图和已作出的决定；派生解释有明确来源与版本 | 产品方向、具体场景、尚未决定的取舍 |
| 工作边界 | 每个进入实施的单元有输入、修改范围、承诺和待履行义务；探索单元有问题与边界 | 单元大小、拆分方式、先后顺序、技术方案 |
| 表达保证 | 明确性质、成立条件、覆盖对象与所需依据，不能用模糊“通过”代替 | 类型、不变量、形式规格、观测或用户评价等具体表达 |
| 进入正式成果 | 核对当前候选与所有必要义务；执行者不能自行写入完成状态 | 每个任务需要哪些义务，以及谁有权决定尚无法机械判断的事项 |
| 变更与修正 | 变更产生新版本；受影响依据须重新成立；用户保留决定不能被静默覆盖 | 在授权范围内重排工作、换实现、调整内部设计 |
| 资源与停止 | 探索遵守已有额度和操作权限；未解决有明确结果，不能靠改名重置 | 具体额度、工具、分工和调度策略 |

固定的是各类决定成立的条件及其后果。上述活动可以往返和交错，不规定所有项目必须走相同数量的阶段、会议或评审角色。

## 3. 最小工作单元

复用已有 Issue、规格文件、Git 版本和工具输出保存信息，不先建设第二套项目数据库。

一个工作单元需要以下内容：

```text
目的：它支持哪个已确认目标，或要澄清哪个具体问题
输入：所依据的规格、代码、依赖和工具配置版本
边界：允许改变什么，必须保持什么，允许哪些环境操作
义务：完成后应当成立的性质，或探索应产生的可检查结果
接纳条件：每项义务需要哪种依据；谁有权改变这个条件
```

算法、文件布局、证明辅助引理等由执行者选择，除非任务本身对此已有约束。

工作单元的制定者同样受约束：

- 拆分出来的子任务要说明如何共同满足父任务；可形式化的部分建立组合证明义务。
- 尚未证明完整性的拆分保持为候选计划；完成子任务不自动等于父任务完成。
- 不要求初级执行者先解决“整体架构一定正确”才能开始探索。
- 能机械检查的边界由工具检查。需要语义判断的部分保留其判断来源，不能包装为机器保证。

## 4. 两条路径与接纳规则

### 探索路径

```text
具体问题 → 有边界的调查/原型/证明尝试 → 可保存的观测与候选方案
```

探索允许未完成代码、暂定规格和失败。候选工作与正式基线隔离；环境操作受到现有权限和资源限制。Git 保存版本，实际副作用仍需宿主的隔离与工具权限约束。

有效探索可能产出：可重放的反例、经过核对的新事实、可行候选或明确的未解决义务。单纯换一段解释、重复同一失败、证明超时都不自动算作推进。

### 建立保证的路径

```text
当前任务规格 + 候选实现
        ↓
履行明确义务：构造约束 / 静态检查 / 证明 / 指定观测或评价
        ↓
可信执行入口核对对象、版本、前提和覆盖
        ↓
接纳该范围内的成果，或保留候选并返回具体未完成项
```

探索结果可以进入候选实现，也可以用于提出新任务规格；不能直接变成已建立保证。

接纳一项改动必须同时满足：

1. 改动依据的任务规格与基线仍是当前版本。
2. 指定义务已经按各自要求得到对应依据，且依据针对实际候选。
3. 被依赖的前提已履行，或属于明确允许的信任边界；仍未履行的前提使结论保持条件性。
4. 实际生产入口使用了被检查的实现；无法确认的接线不计入保证。
5. 仍然有效的既有承诺得到保持，或其变更已在相应决定权限内处理。
6. 接纳是原子的：核对失败不会改变正式基线。

满足条件的内部改动可在已有授权内接纳，不增加逐次询问用户的要求。最终产品效果仍由已约定的验收方评价。

## 5. 把错误状态从表达中排除

避免让一段可编辑文字或 `passed: true` 成为接纳凭据。首版接口设计使用不同结果类型：

| 结果 | 能支持什么 |
|---|---|
| 观测记录 | 指定版本、输入和环境下实际发生了什么 |
| 证明检查结果 | 在明确规格和信任前提下，指定实现的某项性质已获检查 |
| 决定记录 | 有权作该决定的人或机制，在什么范围作了什么决定 |
| 未解决结果 | 哪项义务仍缺少什么，不支持完成声明 |

这些类别不能相互隐式转换。例如，运行一组测试成功不能构造“全输入性质已证明”的结果。

“可接纳改动”使用隐藏构造入口的类型表示。接纳器仅接受该类型；正常执行者提交候选，只有核对全部义务的受控入口才能构造可接纳结果。

版本关系在运行时核对，不能只靠 Rust 类型名表达文件内容身份。读取序列化结果时重新验证来源与绑定信息；不信任执行者提交的状态字段。

候选执行者不能同时修改接纳器、检查配置和被保护规格后为自己签发结果。流程本身的修改作为单独版本处理，继续遵守已有权限；这里尚未指定部署和权限设施。

## 6. 形式表达与现有工具

针对可表达的正确性要求，优先选用能承担该要求的强机制：

1. **通过数据结构、封装和类型排除非法状态。** 检查唯一构造路径和保持不变量的操作，避免要求每个调用者记住额外约定。
2. **用已有证明工具建立剩余性质。** 例如用 Verus 分开写规格、证明和实际执行代码，并让验证覆盖实际使用的函数。
3. **对剩余环境行为保留观测。** 集成运行、性能测量和试用回答具体问题，不冒充通用正确性证明。

这些是按性质选择表达的原则，不是机械地给证据排一个通用分数。错误的规格即使被证明，也不能支撑原来的用户目标。

普通测试的薄弱点是有限输入和判定依据：测试运行可以核对，测试程序或判定器本身也可以形式化验证，但仅凭一般测试通过不能推出未覆盖执行的正确性。形式证明与用户意图之间的对应关系，也需要单独处理。

Verus 接入必须记录：实际被检实现、规格、工具版本、配置、依赖，以及允许的外部假设。缺少目标、工具失败、跳过目标或超时均为未建立；并不自动证明程序错误。`assume`、`external_body` 等不能在未处理信任边界变化时被用来补齐缺失证明。官方文档明确说明这些机制引入的依赖条件。[Verus 信任边界](https://verus-lang.github.io/verus/guide/tcb.html)

特别注意调用边界：未验证代码调用已验证函数时，Verus不会自动检查外部调用者是否满足前置条件。可通过验证调用方、把前提封装进受控构造的类型，或运行时检查来承担对应责任；采用哪种方式由任务决定。[Verus 调用边界](https://verus-lang.github.io/verus/guide/call-from-unverified-code.html)

## 7. 给初级程序员的操作规则

| 看到什么 | 可以做什么 | 结果如何处理 |
|---|---|---|
| 义务明确，输入齐全 | 在候选范围内实现；增加辅助引理或调整内部表示 | 交由规定检查入口建立依据 |
| 不知道某个环境事实 | 阅读实际定义，做受限探针或原型 | 保存事实及其范围，继续或修改候选 |
| 发现可重放反例 | 定位违反的性质及所用版本 | 撤回受反例影响的结论，保留其他仍有效工作 |
| 证明没有完成 | 修实现、补引理、查前提，或记录具体卡住的义务 | 保持未解决；不能擅自加强前提或删除目标来获得通过 |
| 子任务完成但集成未成立 | 检查父任务仍未履行的组合义务 | 子任务成果可以保留，父任务不标完成 |
| 需要改变任务承诺 | 提出有版本的新方案及影响 | 在已有决定权限内修订；触及用户保留决定时找用户 |
| 当前工作全部义务满足 | 提交候选及原始依据 | 接纳器核对并接纳，继续下一个具备条件的单元 |
| 无法继续且额度耗尽 | 提交未完成义务、已得结果与所需条件 | 保留有效成果；由项目调度在既有授权内换任务或重分资源 |

单个单元卡住不自动暂停整个项目。调度者可以继续其他已具备条件的工作；任务选择的质量仍是开放决策，不宣称已由这些规则解决。

## 8. PL 例子：漏登记不应只靠执行者记住

考虑已经约定的性质：同一声明域的独立泛型参数不能被推断错误地合并；合法调用的实参则可以相同。

弱接口让调用者先逐个登记，再调用合并函数。只证明合并函数保持“已经登记”的关系，不能覆盖漏登记。

候选设计是：从真实声明生成一个隐藏构造入口的声明域对象；只有该对象能创建推断状态。登记成为这条构造路径的一部分，后续合并操作保持其不变量。

需要分别建立的义务：

- 声明域对象包含语义所要求的全部独立关系，且映射来自真实输入。
- 合并操作保持这些关系，拒绝时不改变相应状态。
- 满足可合并条件的输入能成功；不能仅证明“拒绝所有输入也不会错误合并”。
- 实际入口经过该构造路径；其他入口不能绕过它创建状态。

执行者可以自由选择内部存储结构和辅助证明。只要上述义务未闭合，系统就不能把“核心证明通过”表达成“整个泛型入口正确”。

这是一项设计提案，尚未对现有 Vorton 实现作改动或证明。

## 9. 固定核心自身要证明什么

若进入实现阶段，直接对实际使用的状态转换代码建立以下不变量，避免另写一个与生产实现脱节的理想模型：

```text
接纳 ⇒ 指定义务均有匹配且当前有效的依据
接纳 ⇒ 依据绑定当前规格、候选及必要依赖
接纳失败 ⇒ 正式基线保持不变
未解决 / 观测结果 ⇏ 形式证明结果
规格或相关输入改变 ⇒ 旧依据不得原样支持新对象
用户保留决定改变 ⇒ 存在对应的有效决定记录
```

这些性质可用 Rust 的封装和类型系统承担一部分，再用 Verus 验证动态状态关系。首版复用 Git、项目构建工具和现有验证器。

证明仍依赖执行入口、文件与工具结果绑定、权限隔离、验证器和所用规格。它不能自动证明自然语言目标已经被完整转成义务，也不能保证调度总能找到成功路线。

## 10. 下一份可实现规格

本草案已经划定固定规则与任务自由度。进入编码前，只需把一个最小工作单元具体化：

- 选择真实、边界明确的工作单元及它的正式义务。
- 固定候选、规格与依据的实际版本绑定方式。
- 定义接纳入口及失败不改变基线的行为。
- 对这条实际路径建立上述不变量，给出一个被拒绝的缺证据候选与一个可接纳候选。

“缺证据就被拒绝”只验证限制能力；可接纳候选必须同时存在，才能说明这条路径确实支持推进。它仍只验证这个最小工作单元，不能替代开放项目全过程的后续检验。
