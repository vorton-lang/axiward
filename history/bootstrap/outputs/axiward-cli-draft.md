# Axiward CLI 设计草稿

2026-09-17 · 第 1–13 条交互选择已确认；命令名称与流程映射为草案。已完成 Codex 原生命令规则的匹配检查，完整集成尚未验证。

本文细化已有的 [系统设计](https://github.com/vorton-lang/axiward/discussions/1)。Axiward 通过 CLI 管理项目视图和正式状态，复用原生 harness（agent 运行环境）的权限与执行设施。原有四类动作、证明要求和信任边界继续适用。

## 已确认的选择

### 项目边界

1. Axiward 以 CLI 为入口，没有自身的常驻守护进程。权限等原语借助原生 harness，约束作用于具体任务对项目的访问，不独占整个 harness。
2. 原生 harness 的项目目录只包含 Axiward 提供的文件视图，真实 Git 仓库放在该项目目录之外。Agent 不直接接触真实仓库，仍可使用原生文件读取、搜索和编辑工具操作视图。
3. 控制范围是项目世界。外部资料与环境通常开放；需要作为项目依据接纳的内容，仍遵守已有的证据规则。

### 工作包与材料访问

4. 每个工作包绑定领取时的固定输入快照。候选内容可以编辑，提交时按最新根与实际依赖重新核验。
5. 同一节点同时只有一个活动工作包，不同节点可以并行。
6. 占用没有内置有效期，不自动回收。未提交且未明确结束就保持活动；包结束或显式取消后释放。限时管理可以由外部负责。
7. 普通项目资料默认可申请读取，明确的访问限制除外。读取权限由规范决定，初始视图按任务裁剪；未导出的材料不自动等于禁止读取。
8. `next` 提供简短项目地图；`search` 检索固定快照中的全部可读材料；`view add` 按权限补充材料。目录与索引根据真实快照和精化图生成。

### 状态、决策与执行

9. 用户通过独立的 `decide` 入口作决定，该确认入口不授权给 agent。记录决定后，通知等待该答复的原任务继续。
10. 源码、规格、精化图和需要保留的推进记录，共用一条 Git 提交历史。一次正式状态转换形成一份完整快照；只更新系统状态的提交也允许存在。
11. 项目实验由原生 harness 执行，harness 直接向 Axiward 提供实际执行记录；agent 提供结果解释。
12. 首版沿用同一 agent 会话处理后续工作包。只有实测显示问题，才考虑上下文隔离。文件权限变化不承诺清除既有上下文。
13. 探索的中间记录持续保存；探索成果在工作包结束时统一提交、核验入图。探索方案本身的准入仍在运行前完成。可以提前结束探索并提交已有成果，再由下一轮导航决定后续动作。

## 命令草案

命令名称暂定；四类动作由主循环分派，执行者不能通过参数自行换类。

| 命令 | 职责 |
| --- | --- |
| `axiward status` | 显示当前状态、工作包与具体阻碍。 |
| `axiward next` | 按调度与导航结果分配工作包，登记占用，提供固定快照的文件视图及项目地图。 |
| `axiward search <查询>` | 返回可读材料的资源 ID、位置与简短摘录，覆盖尚未导出的材料。 |
| `axiward view add <资源ID>` | 核验读取权限，从工作包绑定的快照补充材料；不改变目标命题或精化结构。 |
| `axiward prepare <探索方案>` | 探索开始前，核验方案、合规证明和结果解释规则；准入通过后才能开展对应项目实验。 |
| `axiward submit <结果包>` | 核验最终候选、证明及执行依据，记录结果并按固定流程结束工作包。 |
| `axiward cancel` | 显式结束工作包，保留相关候选及记录，释放节点占用。 |
| `axiward decide <待决事项>` | 接收用户决定，按规定更新状态并通知原任务。 |

`prepare` 是原设计“执行前准入”的接口映射建议。它是探索流程中的步骤，不增加第五类动作；具体参数和数据格式尚未定稿。

## 四类工作包如何使用这些入口

14. **精化**：领取工作包后，生成子目标、依赖、组合方式和证明，通过 `submit` 提交。
15. **执行**：领取工作包后，一次性提交实现与证明。未通过核验就返回主循环，不在原包内反复修补重交。
16. **探索**：先准备并核验探索方案，再由 harness 按获准契约运行、记录；结束时通过 `submit` 提交结果。
17. **请求决定**：通过 `submit` 提交具体问题、权限依据与已知答复分支。用户通过 `decide` 答复；等待仅阻塞依赖该决定的工作。

四类流程沿用已有系统设计。核验通过、操作被接纳、目标节点闭合、整个项目完成，是不同状态，CLI 返回值必须区分。

## 接入机制与待验证部分

18. **权限分离**：真实仓库放在任务项目目录外，通过 harness 的路径权限禁止 agent 直接读写。对 Codex，已找到原生组合：路径权限限制普通命令，命令规则单独允许 Axiward 的指定子命令在沙箱外执行。规则检查已通过，实际拒读与 CLI 例外仍需联测；放在目录外本身不等于禁止读取。
19. **执行记录**：需要绑定实际调用、源码或候选版本、运行环境及结果。记录必须来自受信的 harness 通道；仅有 agent 提交的文本日志不满足这个要求。
20. **任务通知**：需要准确定位等待答复的任务。原任务不可达或通知失败时，应保留已记录的决定并明确报告，不把通知成功当作必然。

这些接入要求仍需分别验证。已完成的原生规则检查不等于完整隔离保证；不同 harness 的实现需要分别取证。

以 Codex 为例，官方文档提供了以下接入线索：

- [Hooks](https://learn.chatgpt.com/docs/hooks#tool-coverage)：支持多类工具的前后事件，但存在覆盖例外，官方明确不将其视为完整的强制执行边界。`PostToolUse` 输出也不能直接假定为完整原始日志。
- [路径权限](https://learn.chatgpt.com/docs/permissions#filesystem-permissions)：Codex 的权限配置支持按路径设置 `read`、`write`、`deny`，其中 `deny` 同时禁止读取与写入。该配置仍为 beta，主要约束本地沙箱命令；MCP 等入口另有控制。需要实测它与受控 CLI 仓库访问入口的组合。
- [命令规则](https://learn.chatgpt.com/docs/agent-configuration/rules)：`prefix_rule` 的 `allow` 允许匹配命令无需提示地在沙箱外运行，`forbidden` 则阻止调用。应按受保护的可执行文件绝对路径和具体子命令放行；`decide` 不向 agent 放行。该功能仍标为 experimental。
- [任务生命周期](https://learn.chatgpt.com/docs/app-server#lifecycle-overview)：提供恢复任务、开始一轮和追加输入的接口；对现有原生任务的实际接入仍需核实。

### 本机检查记录

使用本机 `codex-cli 0.154.0-alpha.6.2` 的 `codex execpolicy check` 检查独立探针规则，未安装规则或修改现有配置，也未执行示例 CLI。

| 待匹配命令 | 检查结果 |
| --- | --- |
| 指定绝对路径的 `axiward.exe status` | `allow` |
| 指定绝对路径的 `axiward.exe submit` | `allow` |
| 指定绝对路径的 `axiward.exe decide` | `forbidden` |
| 其他路径的同名程序 | 无匹配规则，不获得本例外 |
| 普通 PowerShell 读取命令 | 无匹配规则，不获得本例外 |

放行只提供调用能力，Axiward 仍须核验命令参数和实际状态转换。CLI 程序、权限规则与核验配置属于需要保护的基础设施；不得把这项例外扩展为运行任意 shell 或候选代码的入口。
