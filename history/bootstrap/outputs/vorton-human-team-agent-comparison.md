# 从“做一门 cool 的 PL”到交付：人类团队与 agent 对照

日期：2026-09-16。

这是结合真实语言项目实践构造的团队推演，用于定位研究问题。它不是某个团队的完整历史记录，也不是已经完成的人与 agent 对照实验。人类一侧描述合格团队应提供的能力；agent 一侧列出需要测量的失效风险。

## 先看完整过程

**开放意图 → 形成产品方向 → 试探关键难点 → 交付可运行版本 → 持续集成与试用 → 完整验收。**

过程允许往返。例如，原型暴露不可接受的限制后，团队会调整技术方案；若必须改变用户期待的效果，再带着具体取舍找用户。方向对齐与验收由用户参与，工程调查、实现和日常调度由团队承担。

这里至少有三项责任需要被持续承担：对产品效果负责、对整个系统可实现且一致负责、对验证和实际使用负责。它们可以由少数人兼任，不预先要求三个 agent 或某种组织结构。

## 1. 团队如何推进，直接替换后哪里可能断

| 活动 | 资深团队的具体工作与产物 | 换成 agent 后要测的风险 |
|---|---|---|
| 让“cool”变得可以讨论 | 调查已有语言，写出几组能展示差异的示例，提出方向与推荐。用户评价想要哪种体验。形成初步产品方向、代表场景和暂不追求的目标 | 很快罗列高级特性并形成庞大规格；用户尚未认可的解释被当成既定要求。或把内部技术选型全部转成用户问卷 |
| 弄清关键难点 | 选最影响可行性的几个问题，做小原型与反例实验。产物是可观察结果、限制和路线取舍依据 | 以熟悉的架构描述代替实际验证；只做容易成功的样例，把尚未验证的组合能力写成已成立 |
| 组织实现与分工 | 约定模块输入输出、关键语义和依赖；安排先跑通用户场景的工作次序。明确谁负责集成，以及哪些结论仍暂定 | 各执行者依据不同版本的假设工作；完成了大量局部模块，却没有人持续核对完整用户路径 |
| 形成可运行版本 | 从源程序输入一路运行到结果与诊断；再逐步覆盖已约定的场景。保留完整目标的未完成清单 | 演示程序被特殊照顾，主路径尚不通；或把早期原型的成功扩展成整门语言完成 |
| 处理异常与改路 | 减小复现，区分实现错误、设计问题和误解目标；核查受影响的假设与消费者，然后修复或调整路线 | 每次只解释当前报错，换了诊断却继续依赖旧前提；同类问题在不同入口持续出现 |
| 验证体验与质量 | 用语言写新的实际程序，检查表达是否自然、诊断是否可用；检验实现符合约定，并根据试用结果修订方案 | 自己生成实现和测试，两边共享遗漏；所有已知样例通过，却没有证据支持更广的可用性 |
| 收敛并交付 | 在干净环境按说明安装、运行，核对已承诺能力与剩余限制，提交可验收的产品。用户评价效果 | 测试通过数、任务完成数或最终报告代替完整交付；功能实际不支持，但总结声称已经完成 |

这些风险也会发生在人类团队中。比较时要观察发生频率、纠正速度、返工成本和所需人工接管量，而不是假定人总能做对。

## 2. 用一个具体片段观察工程责任

以下假设仅用于推演：用户在看到示例后偏好“代码简洁、错误尽早发现、诊断好理解”的方向。这不是为 Vorton 新增已批准要求。

团队先展示一小段目标语言代码及预期诊断，再完成一条真实执行路径。随后用一个跨模块、带泛型调用的小工具检验组合能力。

假设遇到这种情况：简单泛型调用正常，一旦跨模块，合法程序却被拒绝。修复一处后，另一类同样合法的程序又失败。

合格团队此时需要承担的工作：

1. 把错误缩小到能清楚展示差异的程序，并核对期望来自哪项已约定语义。
2. 检查它与此前失败是否共享同一个前提，例如泛型信息跨模块传递是否完整。
3. 找到信息的生产者、传递边界和实际消费者；决定继续局部修复，还是调整内部表示。
4. 在新的候选上重跑合法和非法对照，恢复实际用户场景。
5. 如果修复保持已约定效果，就由团队推进；如果只能通过放弃用户承诺的能力解决，再说明代价并讨论取舍。

在 agent 运行中，可以直接观察以下差异：

- 它是否读取实际接口与原始结果，还是根据命名猜测？
- 它是否把第二次失败用于修订先前判断，还是只增加一项待修 bug？
- 评审者是否检查信息如何经过真实入口，还是只确认核心算法和已有测试？
- 修复后，它核对的是完整场景还是最后一个报错？
- 如果需要改变产品语义，是否在依赖该变化之前找用户对齐？

这里研究的是一组可观察行为。只出现某种错误，还不足以确定原因来自模型能力、上下文管理、工具可用性或流程设置。

## 3. 人类团队实际依赖哪些支持

| 支持 | 在这个项目里如何起作用 | 对 agent 的具体调查 |
|---|---|---|
| 领域经验与案例 | 用已见过的语言与工程问题提出方向，识别高代价设计 | 是否拥有并正确应用相关知识？是否会主动补齐未知部分？ |
| 对当前系统的整体理解 | 知道一处变化会影响哪些语义、接口和用户场景 | 能否从当前代码、规格和依赖中重建理解，而不是沿用过期摘要？ |
| 持久记录与责任连续性 | 代码、决策理由、任务和验证结果帮助团队跨天、跨人继续工作 | 记录是否正确且被实际使用？交接后能否区分事实、假设、用户决定与未完成项？ |
| 多种实际接触 | 语言设计者看表达，编译器开发者看实现，使用者看任务是否好做，验证者检查承诺 | 不同角色是否取得新的材料和观测，还是围绕同一份叙述重复判断？ |
| 工作优先级与判断更新 | 把时间用于关键不确定性，保留可用成果，遇到反证调整投入 | 下一步是否由项目状态决定？是否持续处理最显眼的局部错误而忽略主要障碍？ |

不能从“模型能在一次对话里解释这些原则”推出“agent 能在长期项目中稳定执行”。同样，增加会议或角色数量本身也没有完成上述责任。

## 4. 已有证据能支持到哪里

### Go：设计选择与真实工程问题相连

Rob Pike 的回顾把 Go 的出发点放在 Google 当时的构建速度、依赖、规模和维护困难上。它可以支持我们检查“语言方案是否服务于明确的工作体验”，但不能证明本文每个推演步骤都在 Go 项目中按同样次序发生。

来源：[Go at Google: Language Design in the Service of Software Engineering](https://go.dev/talks/2012/splash.article)。

### Rust：从提案到稳定功能需要不同阶段的证据

Rust 的 RFC 流程要求阐述动机、影响和替代方案；稳定化还要求说明实现期间的设计变化、未决问题以及功能实现和测试覆盖。它为区分“方案获认可”和“产品能力已落实”提供了具体工程参照。

来源：[RFC 流程](https://rust-lang.github.io/rfcs/introduction.html)、[稳定化要求](https://lang-team.rust-lang.org/how_to/stabilize.html)。

### FeatureBench：跨文件理解和可用反馈确实影响 agent 表现

论文在其受测配置中记录了跨文件依赖遗漏、猜测接口而未读取定义等现象；给出准确测试的实验也显示任务完成表现改善。这支持调查上下文核对和反馈使用。其任务以功能和接口为依据，不能直接证明从“cool”形成产品方向时会发生什么，也不能把受测结果当作所有当前模型的能力结论。

来源：[FeatureBench，v1，第 4 节](https://arxiv.org/html/2602.10975v1)。

### 多 agent 研究：角色安排仍需通过实际运行检验

《Why Do Multi-Agent LLM Systems Fail?》在其分析系统中识别了规格与系统设计、agent 间协作、任务验证与终止等类别的问题。可以借用其分类检查交接和验收，但具体到 Vorton 的发生频率与根因仍需测量。

来源：[研究，v1](https://arxiv.org/html/2503.13657v1)。

## 5. 对 Vorton 的研究结果与下一项议程

本轮形成了过程与风险的第一版对照，尚未进行 agent 对照实验。

优先调查三个贯穿项目的转换：

1. **愿望如何变成具体承诺**：谁提出方向，什么观测促成用户认可，哪些细节留给实现者决定？
2. **局部证据如何更新整体判断**：一次失败影响哪些原有结论，局部通过能支持多大范围？
3. **整体判断如何改变后续工作**：谁重排优先级、组织依赖、推动集成，并持续核对最终产品？

建议下一项产物是一份“关键决策点记录”：从最早的产品方向开始，逐点记录当时知道什么、可作哪些决定、需要什么反馈、是否需要用户，以及决定后如何检查结果。先选择真实项目记录中的节点；本文的推演用于提出检查问题，不能替代原始证据。

对比实验应保留同一目标、可用材料和工具，并区分正常的产品对齐与用户接管工程判断。先测出缺口，再决定需要提示、工具、状态记录、模型能力还是其他机制。
