## R0：首个交付目标（已确认）

交付一个可实际使用的 Axiward 版本：在当前 Windows + Codex 环境与一套固定的验证工具链上，让 agent 从用户确认的规格出发，通过受控工作包交付一个小型软件项目。

验收要求：

1. 精化、执行、探索、请求决定四类流程能够真实运行，并遵守既定的准入和结果接纳规则。
2. 正式成果绑定实际源码、当前规格和经机器核验的证明；根与必要过程义务闭合后才宣布完成。
3. Axiward 状态内核的实现接受机器核验；Git、harness、验证器等外部设施的可信假设和实际调用对应关系明确。
4. 暂停恢复、失败留档、规格变更后的复核与复用，以及不同节点并行，都符合已有设计。
5. 用户负责确认规格、必要决定和最终验收，agent 负责完成项目工作。

验收项目与 Q0 行为规格已确认。用户选择优先验证 Lean 4；最终实现栈与具体版本仍以最小实验的结果为依据，导航实现尚未定稿。

## D1：首个验收项目（已确认）

选择有界 FIFO 队列库，作为 Axiward 的首个验收项目。交付目标仍然是 R0 所定义的 Axiward 版本。

## Q0：队列行为规格（已确认）

1. 提供单线程内存队列。创建时指定固定容量 N，允许 N 为 0，初始队列为空。
2. 未满时入队成功，新元素按原值加入队尾。
3. 已满时入队明确失败，队列内容与顺序不变。
4. 非空时出队成功，返回并移除队首元素，不改写元素。
5. 空队列出队返回“空”，队列不变。
6. 长度查询等于实际元素个数；所有操作后均满足 0 ≤ 长度 ≤ N，容量保持不变。

这些是已确认的人类可读行为要求。其 Lean 表达需要保持上述含义，并在验证路线探索中核对语义对应关系；目前尚无已完成的队列实现或证明。

## D3：验证路线优先级（已确认）

优先验证 Lean 4，分别检查：Q0 的表达与证明、实际可执行实现的对应关系、对候选证明的可信审查。该选择不自动确定整个 CLI 都用 Lean 编写，也不自动接受未核实的编译或隔离假设。

| M0：验证关键接入 | harness 接入证据，以及实际产物的验证路线 | 实测仓库拒读与受控 CLI 访问；能够绑定真实执行记录并通知指定任务；验证工具能检查目标产物及证明 | R0 确认；验证路线还依赖验收项目的选择 |
| M1：建立状态内核 | 可核验的状态转换实现与 Git 持久化 | 操作准入、节点占用、证据版本和正式状态更新的不变量成立；证明对应实际实现 | M0 的相关前提成立；核心规范完成形式化 |
| M2：接通工作流程 | 文件视图、资料检索、四类工作包与用户决定入口 | 所有正式变更经过内核；实验与用户决定使用正确来源；失败和暂停保留恢复所需状态 | M1；所需 harness 通道可用 |
| M3：完成首个交付 | 一个真实小项目的源码、证明和完整推进记录 | 达到 R0 的验收要求；错误实现、篡改产物、失效证据不能被错误接纳 | M2；具体项目规格已确认 |

M0 的 harness 调查与验证工具链调查可分别推进。后续节点只使用已获得支持的前提；未通过的前提保留为阻碍，不改写为成功。

M0 已细化为 [探索工作包](axiward-m0-work-packages.md)：Lean 实现与证明、权限隔离、可信证明接纳、执行记录、用户决定与恢复。它们目前均为待执行的实验计划。

对应的职责与数据流见 [CLI 架构图](axiward-cli-architecture.md)。图是逻辑模块划分，不预先要求额外服务或软件包。

这是已确认的总体依赖顺序。每个里程碑还需精化成可一次完成或有界探索的工作包，不能直接把整个里程碑视为 one-shot 执行任务。

## 人工模拟执行方式

每个工作包记录：目标节点、动作类别、输入版本、允许的影响、提交物、验收条件、实际结果和证据引用。

每轮从精化、执行、探索、请求决定中选一类。发现证据不足或路线不成立时，保留失败并重新导航；不能通过改写完成标准把失败变成成功。

证据分别标明来源：用户确认、机器核验、实际运行观测、人工审阅、未验证建议。人工审阅和测试通过不标记为形式证明完成。

主观验收项依据根规格明确授权的判断主体处理；批准记录绑定产物、规格版本和验收项。机器核验记录与流程，不能把它表述为对主观品质的独立证明。
