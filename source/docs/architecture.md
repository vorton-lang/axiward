# 实现与信任边界

控制器加载用户确认的规格包；项目内容不编进 Axiward。`Policy` 解释统一接入格式，`Verifier` 绑定实际规格、候选、证明及产物，`Refinement` 检查真实父子命题。FIFO 和后继函数是普通输入，没有项目专用分支。

| 责任 | 当前实现 |
| --- | --- |
| 正式状态与纯转换 | Model、Transition、Proofs、Workflow、Engine |
| 固定验收输入、规格及版本 | Policy、Git 的不可变对象和原有 Scope |
| 实际证明与候选构建 | Verifier、原生 Sandbox harness |
| 子命题到父命题的证明 | Refinement，与执行核验使用同一固定规格 |
| 合并、旧保证重验、组合及保存 | Controller、Git |
| 工作区、交接和资源访问 | Interface、Diagnostics、薄 Python 适配器 |
| 实验与用户问答 | FlowIO、原生 MCP 接口 |

## 固定输入与恢复

`acceptance.json`、正文、独立形式规格、构建材料和依赖一起保存在 `.axiward/policy/` 的 Git 树中。Scope 绑定规格对象、完整 policy 对象和要求引用；包领取时保存当时 Scope。版本文本只是人读标识，内容对象才绑定具体字节。规格草稿和工作视图都是可编辑文件，不改变已保存对象。

Git 保存初始规格及逐次请求/结果。恢复重新执行转换并核对策略、源码、候选、证明、凭据与产物的对象绑定，不使用另一份可单独改写的状态缓存。`adopt` 额外绑定已提交的未验证 source 基线；它不创建发布记录。schema 不兼容或材料缺失必须明确拒绝，不能自动选择另一个内置规格。

共享源码位于 `source/`，其版本从接纳历史推导。控制器按包的基准与当前源码执行三方合入，并在实际合并候选上重验新目标及当前已接纳保证。冲突或核验失败保留封存稿和原因。只有匹配实际 Scope、候选、产物及检查结果的凭据才能发布；写入通过精确 HEAD 的 CAS 防止并发旧结果覆盖新状态。

## 形式含义与实际产物

规格模块独立于候选编译并固定。核验器构造 `proposition arguments` 的实际 Lean 命题，检查声明的 proof 的类型、公理和证明依赖，而不是比较命题名称或候选自报结果。实际构建、模块依赖、候选和产物随凭据绑定；缺必要材料不放行。

固定入口必须真正调用被证明的对象。FIFO 的固定 Main 经由被证明的 subject 执行；后继函数入口调用被证明的 next。这个对应属于接入材料的语义审核，不能由“文件名相同”或“构建成功”推出任意应用符合用户意图。

精化对同一组任意实际 subject 构造子命题到父命题的蕴含，候选提供此关系的证明。节点编号和数组索引只选数据，不构成产品语义。组合仍核验实际共享源码，没有“所有编号覆盖所以根正确”的捷径。

## 外部信任前提

用户对规格及对应关系的确认、控制器/适配器未被绕过、Git、完整 Lean 工具链、编译器、Codex 原生进程服务和操作系统均为外部前提。内核命题、产物内容绑定、实际运行观测与完整产品符合性是不同层次。

Worker 使用完全访问模式；工具白名单不是操作系统隔离。候选核验保留原生 harness。用户要求跳过权限隔离检查；此前宏改写/运行替换反例被自动审查阻断，未执行，也不据此宣称这些外部边界已完整验证。
