## 议题 2：什么状态归 Git，什么状态归 Axiward

以下为 agent 提出的分工，等待讨论：

| Git 管理 | Axiward 管理 |
| --- | --- |
| 文件内容、目录树、对象标识与版本快照。 | 规格、规范、目标、精化与证明依赖，以及材料在项目中的含义。 |
| 提交历史、父子关系、分支与引用。 | 当前路线、工作包归属与阶段、终稿绑定、尝试结果。 |
| 对象保存、按版本读取、引用的条件更新。 | 操作准入、权限、核验与接纳、失效传播、请求幂等。 |
| 保存承载控制状态的文件，与源码和证据一起形成快照。 | 用户决定、在途操作、暂停恢复、成果有效性与完成条件。 |

- Axiward 的状态和必要依据以文件及内容引用存入 Git；恢复时从正式提交重放并检查。它不维护另一份可独立漂移的权威状态。
- Git 决定内容属于哪个版本；Axiward 判断该版本中的证据是否支持当前目标。文件进入 Git 本身不产生核验通过或目标完成的语义。
- 一次正式转换先由 Axiward 检查并构造状态与材料快照，再由 Git 按预期旧版本更新正式引用；更新成功后才对外报告转换生效。并发冲突后的重新检查属于 Axiward。
- Git 的版本切换不能代替 Axiward 对过程义务和已发生外部操作的处理。

以上分工用于讨论，尚未形成新的实现改动授权。

## 议题 3：Axiward 自身开发与受管项目的指代

用户明确：

- `axiward` 仓库代表 Axiward 自身的开发工作，不代表 FIFO 等受管项目的开发工作。
- Axiward 自身的开发工作将来也要由 Axiward 管理，因此存在自我指涉；讨论必须区分软件、运行中的控制器和被管理的开发项目。

采用以下名称说明当前理解：

| 指代 | 含义 |
| --- | --- |
| Axiward 软件 | 正在开发的控制系统产品，包括其源码、规格及验证。 |
| Axiward 源码仓库 | 当前 `axiward` 开发仓库，保存 Axiward 自身的开发工作。 |
| Axiward 控制器实例 | 某个确定版本正在运行的程序，负责管理一个目标项目。 |
| 受管项目仓库 | 被该控制器管理的开发工作；可以是 FIFO，也可以是 Axiward 自身。 |

FIFO 项目的规格、候选、证明和交付物属于 FIFO 受管项目。Axiward 源码仓库中的 FIFO 测试夹具用于验证控制系统，不因此把控制系统开发和 FIFO 项目开发合为一件工作；本地测试运行目录的位置也不改变其所属项目。

Agent 对自我管理关系的解释：正在运行的 Axiward 版本 A，可以管理 Axiward 源码仓库中候选版本 B 的开发。A 是控制者，B 是被开发和核验的对象；修改 B 的源码不等于修改 A 当前执行的规则。B 的接纳、交付与替换当前控制器是需要区分的事件。具体如何切换控制器、如何引导首个受管版本尚未讨论，不记为已批准方案。

## 议题 5：控制器与 worker 的交互生命周期

用户当前理解：worker 在受限沙箱内工作，看到 Axiward 提供的工作视图，做四选一，操作，然后提交审核。

以下记录当前实现的实际顺序，不将实现现状自动视为用户已确认的最终交互设计。依据：[Interface.next / exportView](../Axiward/Interface.lean)、[MCP worker 工具](../adapter/server.py)、[Controller.check](../Axiward/Controller.lean)。

1. 已创建的原生任务绑定 worker 身份和包工作视图。每个新包可以使用全新 worker；继续使用原身份也不依赖此前上下文。控制器与薄适配器不自行调用模型或创建下一轮模型会话。当前 worker 使用完全访问模式并遵守说明约定。
2. `status` 返回项目概要、节点和完整项目层交接。这是动作选择前可取得的信息。
3. Worker 依据状态与交接明确选择节点和动作，调用 `next` 提交选择。控制器核准领取后固定工作包归属、动作与输入快照，再导出该包的详细工作视图。省略选择只用于恢复空间已绑定的包，不自动分派新包。
4. Worker 在视图中读取规格、目标、交接和操作说明，编辑候选；通过 `search` / `view_add` 补充固定输入材料及明确标记版本的当前记录。领包后不能在包内更换动作类别。
5. 按动作类型调用对应工具，由控制器和受保护适配器处理正式操作：

| 动作 | 当前流程 |
| --- | --- |
| 执行 | 编写实现与证明 → `submit` 封存并核验 → 接纳产物、闭合目标，或拒绝并结束包。 |
| 精化 | 编写方案与组合证明 → `submit` 封存并核验 → 安装子目标、路线或复用结果；新子目标仍待完成。 |
| 探索 | 编写方案 → `prepare` 准入 → 按预算 `experiment` 并登记真实结果 → `conclude` 提交报告、结束包。探索本身不闭合产品目标。 |
| 请求决定 | 编写具体问题 → `submit` 核准登记 → `ask_user` 走独立用户通道 → 保存答复 → 每次相关交接持续提供答复，无须确认已读。当前答复仅产生版本绑定偏好。 |

6. Axiward 保存转换、结果和证据，核验可组合的父目标；worker 根据返回结果进入下一轮。拒绝后修改候选需领取新包；核验中断用 `resume` 继续原封存终稿。项目完成、暂停或等待时，返回对应状态，不能把工作包结束等同于项目完成。

本轮要明确的区别：选择前的项目概要与领取后的详细工作视图不同；四选一由 worker 完成，控制器核准后固定本包动作；探索和用户决定并非全部操作做完后才第一次审核。

### Worker 初始目录与补充材料

用户进一步核对：worker 出生在空白目录，调用 `status` 获得项目地图，领包后获得工作视图，并可额外签出合规文件。

当前实现支持这一整体顺序，具体边界如下：

- “空白目录”指初始不含项目源码和工作包材料的专用视图目录；`session` 已放入 `.codex/config.toml`、`AGENTS.md`、`START.md`，并创建 `work/` 与 `tmp/`。
- `status` 返回项目概要，`next` 核准领包后生成 `work/packages/<node>-<serial>/` 下的规格、目标、操作说明、材料目录及候选目录。
- 额外材料经 `search` 发现、`view_add` 导出到本包 `materials/`。`node/` 材料来自领取时固定快照；`current/` 记录绑定当前返回版本。两者均受现有访问规则约束，worker 不直接操作 Git。
- 当前导出限于控制器资源目录中已列出的规格、目标、历史、证据、先前候选和报告，尚不是按任意仓库路径签出文件的通用接口。依据：[Interface.resources / addResource](../Axiward/Interface.lean)。

### Worker 的 `status` 如何生成

用户询问返回内容的生成方式。当前实现事实：

- Worker 调用的是 MCP `status`。最初适配器分别读取多个组件并组合结果；经 `989e282` 修复，改为一次调用 `worker-status` 统一生成。当前返回状态与完整交接，与直接运行 CLI `axiward status` 的输出不同。
- 组合入口通过一次 `Git.load` 读取正式 `main` 提交中的 `.axiward/state.json`。文件存储初始规格与转换记录；`Engine.restore` 重新计算纯状态转换并核对记录结果，随后检查规格、候选、路线、产物及相关证据的 Git 内容绑定。此过程不重做历史实验或重新运行全部证明核验。
- `status` 部分由恢复出的状态计算：提交 ID、完成/暂停状态、在途操作数、转换次数和项目地图。地图逐个列出节点编号、要求 ID、当前适用性、闭合状态、活动包、阶段和子节点。
- `b84d498` 已用 `handoff` 替代工作侧 `inbox`，按任务、版本和权限计算完整交接，不再按提问者或已读状态省略决定。用户决定是否仍适用会根据当前范围与依赖重新判断。

### 方案：以任务为对象生成完整交接

复用 Git 中已有的目标、路线、工作包、用户决定和操作记录，计算交接视图。使用结构化 `handoff` 取代工作接口中的未读 `inbox`，沿用现有响应和 `view.json`；不持久化另一份交接状态，不新增按 worker 或会话维护的已读表，也不调用模型生成权威摘要。

| 入口 | 必须提供的信息 |
| --- | --- |
| `status` | 当前项目和版本、节点与路线、适用于当前工作的用户决定、待决定事项、暂停与在途操作，足以进行下一步选择。 |
| `next` 领取或重新取得包视图 | 本包目标与动作、固定输入版本、已接纳成果及依赖、相关决定、当前阶段、相关尝试结局与失败原因、在途操作和材料引用。 |
| 封存核验恢复、用户答复等带交接的结果 | 重新生成当时完整的必要交接；不因同一身份、此前送达或已读而省略。 |

### 信息范围与有效性

- 决定不按提问 worker 的身份或 `acknowledged` 过滤。保持决定原有的目标、版本与来源标记，不因展示给另一个 worker 而扩大授权范围。
- 项目层展示当前路线的相关信息；包层覆盖本目标、其当前路线祖先及实际使用的依赖，保留每条信息的适用对象。祖先或依赖上的决定作为带来源的上下文呈现，不自动改写为对子目标的新授权。
- 当前有效决定按已记录的适用性、所绑定目标/版本及当前依赖重新判断。过期、越出既定选项的答复不显示为当前有效指令；历史仍可检索。不能仅凭回答时保存的 `applicable=true` 判断它现在仍适用。
- 对本目标的相关正式尝试保留动作、结局、原因及终稿/证据引用；原始长日志按需读取。关键约束、决定和未解决事项直接出现在交接中，不只给历史链接，也不以任意“最近几条”截断来冒充完整交接。
- 继续遵守现有资料访问规则。若必要交接内容不可见，要明确显示缺失与阻碍，不能静默给出看似完整的交接。

### 快照与生命周期边界

- 一次返回的当前状态与交接复用同一份 `Loaded`，延续刚完成的单快照修复。
- 包的源码、规格和已有材料仍来自领取时固定快照；交接明确区分输入快照与当前状态版本。规格变更、用户后续答复、取消等作为当前变化呈现，不悄悄替换包输入。
- 读交接不写 Git、不消耗消息、不转移工作包归属。它支持每个新包由全新 worker 执行；自动创建 worker 或转交尚被他人占用的包不是本修复新增的机制。
- 失败后换新包或核验中断后恢复原终稿的既有规则保持适用。

### 删除与历史处理

- 删除工作侧 `inbox`/`acknowledge` 的命令、MCP 工具和已读指引，移除当前响应中的未读投递语义，统一使用交接视图。
- 完全删除当前模型中的 `acknowledged` 标记及其更新/过滤逻辑。旧 Git 历史可能已有 `acknowledge` 操作和对应结果，仅保留使这些提交仍可解码/重放的必要支持；不再恢复或维护已读状态。新工作不产生已读操作，不改写既有 Git 历史。
- 此处保留旧重放的具体理由是：直接删除命令类型或结果类型会使现存日志无法解码；并非预建一般化迁移框架。
- 同步更新生成的操作指引、manual 与相关规则说明，去掉必须沿用原会话或读取后必须确认已读的要求。

### 验收与改动范围

验收案例：

1. A 提问并收到用户答复后，完全没有 A 上下文的 B 领取后续相关包，自动得到同一适用决定及必要上下文。
2. 同一身份丢失上下文后重新查询，交接仍完整；重复查询不产生状态变更，历史上已确认已读的决定也不被隐藏。
3. 根规格或依赖变化后，失效决定不会被当作当前指令；包输入保持原快照，当前变化明确可见。
4. 恢复时能看见相关在途操作，不能因更换 worker 而重复执行；跨 worker 的读取不赋予取消或提交别人的包的权限。
5. 并发变化时，当前状态与交接仍对应同一明确提交，保持快照回归的有效性。

实现涉及 `Axiward/Interface.lean`、`Main.lean`、`adapter/server.py`、已读标记相关模型与转换，以及对应检查和说明。保留旧记录重放所必需的最小支持。使用已有流程和原生问答检查验证接合处，增加有实际失败能力的新 worker 交接案例；不扩入核验沙箱或软件配布。

### 当前并发与合入能力

- 正式状态转换通过 Git 引用的比较并更新提交。并发提交中一方先成功，另一方重新加载当前状态、重跑同一转换条件并构造新提交，最多自动尝试八次；持续繁忙时要求保持请求 ID 重试。该机制处理提交顺序竞争，不执行源码三方合并。依据：[Git.transactDetailed](../Axiward/Git.lean)。
- 不同节点的候选、证据和成果写入各自路径；同一节点最多一个活动包。并发不会直接把多个 worker 的源码修改合入同一个工作区文件。
- 当前 FIFO 的父目标组合要求子目标采用同一份 `Queue.lean`，或者由路线显式指定某个子目标提供实现，再组合证明并重新核验父目标。实现不同且未指定来源时，组合失败并保留原因，没有自动解冲突功能。依据：[Refinement.assemble](../Axiward/Refinement.lean)。
- 多包生命周期已向用户说明，尚待判断：包输入固定；无关提交不使包过期；同项目核验进程排队；worker 死亡不释放包；更换父路线不自动取消旧子包；完成条件要求当前路线无活动包且所有在途操作结清。
- 用户已批准冲突后的包生命周期：前包接纳并推进 HEAD；后包遇到冲突时记录原因、结束旧包并保留候选；新包基于新 HEAD，交接提供旧候选及冲突信息；worker 基于这些材料修改，再提交核验。旧包输入快照保持固定、终稿不修改，不新增旧包内解决冲突的中间状态。
- Worker 身份与包生命周期独立：默认使用全新 worker；沿用原 worker 时同样领取新包继续，减少重复工作不要求保留旧包活动状态。
