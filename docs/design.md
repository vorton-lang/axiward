# 已审核设计与交付要求

本文保留已审核的系统设计第 1–71 条、交互选择第 1–13 条和 R0 验收要求。它们规定目标与约束，不代表相应能力均已实现；导航首版方案仍为暂定。当前实现与差距见[路线图](roadmap.md)，操作规则见[状态转换规则](kernel-contract.md)。

## R0 交付要求

交付一个可实际使用的 Axiward 版本：在当前 Windows + Codex 环境与一套固定的验证工具链上，让 agent 从用户确认的规格出发，通过受控工作包交付一个小型软件项目。

验收要求：

1. 精化、执行、探索、请求决定四类流程能够真实运行，并遵守既定的准入和结果接纳规则。
2. 正式成果绑定实际源码、当前规格和经机器核验的证明；根与必要过程义务闭合后才宣布完成。
3. Axiward 状态内核的实现接受机器核验；Git、harness、验证器等外部设施的可信假设和实际调用对应关系明确。
4. 暂停恢复、失败留档、规格变更后的复核与复用，以及不同节点并行，都符合已有设计。
5. 用户负责确认规格、必要决定和最终验收，agent 负责完成项目工作。

首个验收项目为有界 FIFO 队列，已确认的行为要求见[队列规格](product-guide.md#队列规格)。

## 规格与信任根

1. 系统从模糊需求出发，目标是交付满足完整规格的产品。
2. 规格由 skill 辅助产生；需求澄清、规格形成与产品实现可以交错进行。
3. 规格同时具有简洁、人可读的命题表达，以及对应的机器可核验形式。
4. 用户负责确认规格及其形式化含义；系统不承担根规格正确性的责任。
5. 规格是项目要求的唯一信任根；基础设施与验证器的可信前提必须显式建模。

## 精化图与执行

6. 系统维护以规格为根的精化依赖图，记录候选、待证义务、实现、依据和操作。
7. 每次精化都要建立：下层义务成立，足以满足对应的上层义务。
8. 模型选择精化路线，也可提出候选引理和证明策略；模型没有验证或放行权。
9. 系统自动构造、组合并核验证明，使已成立的结论向根传播。
10. 每项系统操作都必须有对应命题，绑定实际输入、输出及版本，并反向溯源到根。
11. 执行前证明操作符合适用的系统规范；执行后核验结果能够支持的结论。
12. 未通过准入证明的操作不得执行；证明失败或超时表示未解决，不等于命题已被证伪。

## 基础设施与验证器

13. 优先复用现有基础设施，将其能力、前提和效果纳入形式模型，并保障实际调用符合模型。
14. 可表达的保证优先由构造约束、类型系统和形式证明承担；普通测试通过仅提供有限观测。
15. 验证器可以相互声明并依赖保证；它们的契约、对应关系和信任边界必须明确。
16. 具体采用哪些验证器取决于项目与系统实现形态，不预先固定为 Lean 或其他单一工具。

## 探索与外部结果

17. 探索针对未闭合义务，改变由候选路线、已有证据和未完成义务构成的求解状态。
18. 探索前核验目标关联、状态保持条件、资源与影响边界，以及各种结果的解释规则。
19. 探索允许失败、未知或没有收获；允许探索不等于保证探索必然推进项目。
20. 经核验的反例可以排除对应候选；没有找到反例不能证明候选正确。
21. 外部建议、论文结论和模型输出可以作为待证命题进入图，不能直接充当已证前提。
22. 执行和测量结果通过已建模的观测契约进入图，只支持对应版本、输入和环境下的事实。
23. 外部证明或证书经适用验证器核验，并满足已声明的信任条件后，才能支持义务闭合。

## 完成保证与规格变更

24. 完成要求根规格与执行过程的全部必要义务闭合，证明绑定实际交付物和完整实际操作。
25. 在可信基础设施符合模型的前提下，完成意味着产品满足当前根规格，过程符合各操作执行时有效的规范。
26. 规格变更不使历史操作变为非法；操作是否允许，取决于执行当时有效的定义。
27. 操作结果是否仍有效，取决于最新根规格；变更影响沿实际依赖关系传播。
28. 不受影响的实现和证明可以复用；受影响部分重新核验，不自动要求重新实现或重复执行。

## 范围

29. 本部分规定操作与成果的核验和接纳条件，不承诺任意命题都能被自动证明或判定。
30. 模型如何选择下一步、如何提高推进效率，留给下一部分设计。

## 生命周期：动作与循环

31. 每轮主循环在给定图和当前工作节点下，从精化、执行、探索、请求决定中选择一类动作。
32. 每类动作对应固定流程；模型在流程允许的步骤和参数中选择，系统拒绝不合规操作。
33. 动作采用粗粒度工作包；图记录动作及必要的子目标，包内语句级生成不拆成导航节点。

## 生命周期：四类工作包

34. 执行表示模型认为当前节点可 one-shot 完成：一次性提交实现 P 及其满足当前规格的证明，包内生成不由系统逐步指导。
35. 执行提交未通过核验时返回主循环，重新四选一，不在本次执行内部自动反复修补。
36. 精化一次性交付子目标、依赖、组合方式，以及子目标全部成立足以满足当前目标的证明；子目标仍待解决。
37. 复用成果和更换路线归入精化；更换当前路线时保留历史与仍有效的成果。
38. 探索交付方案、符合探索契约的证明及结果解释规则；内部可多轮调用模型和工具，但受固定流程、预算和退出条件约束，执行记录保留。
39. 请求决定交付具体问题、关联义务、权限依据，以及已知答复分支对图的影响；模型不代替用户作决定。
40. 请求发出后记录待决状态，仅阻塞依赖该决定的节点，其他独立工作可继续；答复按既定外部输入规则入图。
41. 工作包及其结果由系统核验；合法结果更新图，动作结束或被拒绝后回到主循环。

## 生命周期：尝试历史与导航输入

42. 系统为每次粗粒度尝试自动留档并关联目标节点，包括被拒绝、失败、超时、未解决和成功的尝试。
43. 尝试记录包含动作与方案、所依据的版本、实际结果、资源消耗，以及产物和原始记录的引用。
44. 尝试历史与证明依赖明确区分；模型对失败原因的解释与系统原始结果分开保存。
45. 导航读取当前节点、相关依赖和尝试历史的视图，保留版本及适用范围；长日志和完整产物按需读取。
46. 导航依据这些信息推荐四类动作之一，并引导固定流程中的子操作；接口、评价与调度约定见导航部分。

## 生命周期：等待、暂停与恢复

47. 验证、放行和判定完成由系统负责；等待、暂停和恢复属于系统运行状态，不增加第五类模型动作。
48. 预算耗尽或外部条件阻断本次运行时，系统保存图和具体障碍，以未完成状态暂停，不宣称任务无解。
49. 条件恢复后沿原图继续；已有成果是否可复用，仍按最新根规格核验。

## 形式化接口与开放调研

50. 四类动作必须有形式化的操作定义、参数、前置条件、后置条件和状态转换规则；自然语言流程说明不能直接作为执行依据。
51. 图中的信息区分为形式化命题与操作、结构化执行事实、自然语言解释与建议，分别保留其用途和可信范围。
52. 结构化格式不等于形式化语义；执行结果由系统记录，模型填写的“通过”或“正确”字段不能自行产生证明效力。
53. 只有经核验的命题或按既定观测契约接纳的事实，才能成为证明前提；其他内容可以供导航参考。
54. 技术调研和架构分析属于探索；研究内容可以开放，但过程必须符合明确的输入、工具权限、资源和结果处理契约。
55. 探索方案须落实为已建模操作的组合；工具调用和结果解释均受固定流程约束。
56. 调研输出区分资料引用、候选方案与推荐、经核验的观测或证明；引用可定位不等于其内容已经成立。
57. 推荐方案可以影响导航并成为后续精化候选，不能代替该方案满足规格的证明。
58. 请求决定核验请求权限、答复来源、作用范围和更新规则；系统不从旧规格推导新规格的正确性。
59. 探索过程合规不保证调研充分或推荐优良；这些属于导航需要评价的质量。

## 导航：接口与评价目标

60. value model 是导航评价机制的名称，不预设为 LLM、专用模型或机械系统，具体实现可以替换。
61. 导航输入是当前图、工作节点及相关历史，并包含剩余预算、下游执行模型和流程版本等评分条件。
62. 导航返回推荐的动作类别，或四类动作各自的推荐度；可附文字、图片等形式的理由及相关节点引用。
63. 共同评价目标是在给定资源和用户交互预算内，尽量提高最终完成根规格的概率。
64. 四个推荐度不要求加起来等于 1；分数表达推荐顺序，未经校准时不解释为准确的成功概率。
65. 理由用于解释和复盘，可指出依据的图中事实及预期改变；理由本身不获得证明效力。

## 导航：暂定实现与对照

66. 首版暂定比较机械规则与统计、加载导航 skill 的 clean-context agent，两者使用相同接口；其他实现形态继续开放。
67. 在可回放状态下，固定下游执行器和预算，对照不同推荐的后续结果，评价根规格完成情况、总成本和用户介入量。
68. 单个被选动作的成败不足以证明推荐顺序正确；对照需考虑其他选择可能带来的后续结果。
69. 导航自身的时间和计算消耗计入总成本，其效果依据实际结果评价。

## 导航：节点调度与动作分派

70. 当前工作节点由主循环按可替换的调度规则选择；初版采用简单、确定性的策略，导航接口继续评价给定节点的四类动作。
71. 主循环按导航结果确定本轮动作类别，执行模型只能完成该类工作包；无法完成则记录结果并返回下一轮导航，不能自行换类，也不能绕过系统核验。

## 已确认交互选择

### 项目边界

1. Axiward 以 CLI 为入口，没有自身的常驻守护进程。权限等原语借助原生 harness，约束作用于具体任务对项目的访问，不独占整个 harness。
2. 原生 harness 的项目目录只包含 Axiward 提供的文件视图，真实 Git 仓库放在该项目目录之外。Agent 不直接接触真实仓库，仍可使用原生文件读取、搜索和编辑工具操作视图。
3. 控制范围是项目世界。外部资料与环境通常开放；需要作为项目依据接纳的内容，仍遵守已有的证据规则。

### 工作包与材料访问

4. 每个工作包绑定领取时的固定输入快照。候选内容可以编辑，提交时按最新根与实际依赖重新核验。
5. 同一节点同时只有一个活动工作包，不同节点可以并行。
6. 占用没有内置有效期，不自动回收。未提交且未明确结束就保持活动；包结束或显式取消后释放。限时管理可以由外部负责。
7. 普通项目资料默认可申请读取，明确的访问限制除外。读取权限由规范决定，初始视图按任务裁剪；未导出的材料不自动等于禁止读取。
8. `next` 提供简短项目地图；`search` 检索固定快照中的全部可读材料；`view add` 按权限补充材料。目录与索引根据真实快照和精化图生成。

### 状态、决策与执行

9. 用户通过独立的 `decide` 入口作决定，该确认入口不授权给 agent。记录决定后，通知等待该答复的原任务继续。
10. 源码、规格、精化图和需要保留的推进记录，共用一条 Git 提交历史。一次正式状态转换形成一份完整快照；只更新系统状态的提交也允许存在。
11. 项目实验由原生 harness 执行，harness 直接向 Axiward 提供实际执行记录；agent 提供结果解释。
12. 首版沿用同一 agent 会话处理后续工作包。只有实测显示问题，才考虑上下文隔离。文件权限变化不承诺清除既有上下文。
13. 探索的中间记录持续保存；探索成果在工作包结束时统一提交、核验入图。探索方案本身的准入仍在运行前完成。可以提前结束探索并提交已有成果，再由下一轮导航决定后续动作。
